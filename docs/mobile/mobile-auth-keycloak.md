# Mobile Keycloak Authentication

FOMO-170 — Authorization Code + PKCE via Expo AuthSession.

## Realm assignment

| Client | Realm | Notes |
|---|---|---|
| Mobile app (`fomo-mobile`) | `fomo-users` | End-user realm |
| Dashboard (`fomo-dashboard`) | `fomo-admin` | Internal staff realm |

**Mobile must never authenticate against `fomo-admin`.** That realm is for internal dashboard users only. Using `fomo-admin` from the mobile client will produce a "Client not found" error in Keycloak.

## Architecture

```
User taps Log In
  └─► expo-auth-session (PKCE)
        └─► Keycloak browser flow (Chrome Custom Tab / ASWebAuthSession)
              Realm: fomo-users  Client: fomo-mobile
              └─► redirected back to fomo://
                    └─► code exchange (expo-auth-session)
                          └─► tokens stored in expo-secure-store
                                └─► GET /api/v1/users/me (Bearer token)
                                      └─► app enters Discover tab
```

## App access gate

Mobile is a registered-user experience. The app gates all content behind login:

- **Unauthenticated** → login/welcome screen; no tabs visible
- **Authenticated** → full app; tabs unlocked

The gate is implemented in `app/_layout.tsx` via the `AuthGate` component, which uses `useAuth()` to redirect between `/login` and `/` depending on auth state.

## Required environment variables

Add these to `apps/mobile/.env` (see `.env.example`):

| Variable | Value | Notes |
|---|---|---|
| `EXPO_PUBLIC_AUTH_URL` | `https://auth.staging.fomo-lab.org` | Keycloak base URL |
| `EXPO_PUBLIC_KEYCLOAK_REALM` | `fomo-users` | End-user realm — NOT `fomo-admin` |
| `EXPO_PUBLIC_KEYCLOAK_CLIENT_ID` | `fomo-mobile` | Public client (no secret) |
| `EXPO_PUBLIC_AUTH_REDIRECT_SCHEME` | `fomo` | Must match `scheme` in `app.json` |

## Keycloak client settings (`fomo-users` realm)

The `fomo-mobile` client in the **`fomo-users`** realm must be configured with:

| Setting | Value |
|---|---|
| Client type | OpenID Connect |
| Access type | Public |
| Standard flow | Enabled |
| Direct access grants | Disabled |
| Valid redirect URIs | `fomo://*` |
| Web origins | `+` (use Valid Redirect URIs) |
| PKCE method | S256 |

**Valid redirect URIs**: `fomo://*` covers the URI generated by `makeRedirectUri({ scheme: 'fomo' })`.
The exact URI logged in dev (`[auth] redirect URI: fomo://`) must appear in this list.

## Issuer and discovery

- **Issuer**: `https://auth.staging.fomo-lab.org/realms/fomo-users`
- **OIDC discovery URL**: `https://auth.staging.fomo-lab.org/realms/fomo-users/.well-known/openid-configuration`

## Redirect URI

`makeRedirectUri({ scheme: 'fomo' })` produces `fomo://` on Android native dev builds.
This is emitted to the dev console on startup: `[auth] redirect URI: fomo://`

## Backend JWT compatibility

The API (`/api/v1/users/me`) validates the `iss` claim against `AUTH_OIDC_ISSUER` plus any
issuers listed in `AUTH_OIDC_EXTRA_ISSUERS`.

**Required staging backend config:**

```env
AUTH_OIDC_ISSUER=https://auth.staging.fomo-lab.org/realms/fomo-admin
AUTH_OIDC_EXTRA_ISSUERS=https://auth.staging.fomo-lab.org/realms/fomo-users
AUTH_OIDC_ALLOWED_AZP=fomo-dashboard,fomo-mobile
```

`fomo-users` JWTs are accepted via `AUTH_OIDC_EXTRA_ISSUERS`.
The JWKS URL is derived automatically as `{issuer}/protocol/openid-connect/certs`.

## Token storage

Tokens are stored using `expo-secure-store` (Keystore on Android, Keychain on iOS):

| Key | Content |
|---|---|
| `fomo_access_token` | Keycloak access token (JWT) |
| `fomo_refresh_token` | Keycloak refresh token |

Tokens are **never** logged or passed through UI component props.

## Session lifecycle

1. **App start** — `AuthGate` shows a loading spinner while `AuthProvider` restores the session.
   - Tries refresh token first; falls back to access token; clears and redirects to `/login` on failure.
2. **Login** — Chrome Custom Tab (Android) / ASWebAuthSession (iOS) opens Keycloak `fomo-users`.
   - Code exchange returns tokens; stored securely; `AuthGate` redirects to `/`.
3. **Logout** — clears all tokens; `AuthGate` redirects to `/login`.
4. **Session expiry** — failed token refresh clears session and redirects to login gate.

## Old-realm token cleanup

If a device previously stored tokens from the `fomo-admin` realm, the refresh token exchange
will fail (wrong issuer endpoint). `AuthProvider` detects this failure and calls `clearTokens()`,
returning the user to the login screen. No crash occurs.

To manually clear: `adb shell pm clear com.fomo.mobile` or uninstall + reinstall.

## How `/api/v1/users/me` is called

After a successful code exchange, the auth provider calls:

```
GET https://api.staging.fomo-lab.org/api/v1/users/me
Authorization: Bearer <access_token>
```

The backend validates the JWT against the `fomo-users` JWKS endpoint and creates the FOMO
user + default profile on first access (idempotent). Returns `UserMeResponse`.

## Testing login/logout

1. Clear app data: `adb shell pm clear com.fomo.mobile`
2. Open the app — login/welcome gate should appear (not Discover).
3. Tap **Log In** — Chrome Custom Tab opens Keycloak `fomo-users` realm.
4. Enter credentials → submit.
5. App returns to Discover tab (authenticated).
6. Open Profile tab — shows username, email, system_role from `/users/me`.
7. Tap **Log Out** — returns to login gate.
8. Restart app — session restores silently if tokens are still valid.

## Known limitations / follow-ups

- **Logout does not invalidate the Keycloak browser session**: a subsequent login tap may
  re-authenticate silently. Call the `end_session` endpoint to force re-login.
- **iOS not tested**: redirect URI `fomo://` should work; requires same Keycloak config.
- **Saved / Interested / Going**: deferred (FOMO-170 scope). Auth layer is in place.
- **Profile editing**: deferred.
